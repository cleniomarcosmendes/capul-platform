## Achados Altos

### Achado #A1 — Healthchecks rasos em 3 dos 4 backends

- **Dimensão:** 6 (Observabilidade) + 4 (Robustez)
- **Severidade:** **Alto**
- **Localização:**
  - `auth-gateway/src/health/health.controller.ts` — só checa DB
  - `gestao-ti/backend/src/health/health.controller.ts` — só checa DB
  - `inventario/backend/app/main.py:730` — só checa DB
  - `fiscal/backend/src/health/health.controller.ts` — **CORRETO** (DB + Redis + SMTP + SefazTLS) → modelo a replicar

- **Descrição:** Os 3 backends Node + FastAPI usam healthcheck que só executa `SELECT 1` no Postgres. Não verificam Redis (que aloca sessões, throttler, BullMQ), nem SMTP (alertas). Container fica "healthy" no Docker mesmo com Redis caído.

- **Por que é problema:**
  - Redis down → throttler para de funcionar → brute force passa
  - Redis down → sessões JWT refresh falham → usuário desloga
  - Redis down → BullMQ travado → CT-es param de baixar
  - Tudo isso com healthcheck retornando 200 → orquestrador não detecta nada
  - Auth-gateway é o gateway central — falha silenciosa aqui propaga
  - `fiscal-backend` já tem o exemplo certo: 3 níveis (`ok`/`degraded`/`down`)

- **Evidência:**
  ```typescript
  // auth-gateway/src/health/health.controller.ts (raso)
  async check() {
    let database = { ok: false, latencyMs: -1 };
    try { await this.prisma.$queryRaw`SELECT 1`; database.ok = true; } catch {}
    return { status: database.ok ? 'ok' : 'down', checks: { database } };
  }
  ```
  vs
  ```typescript
  // fiscal-backend (profundo)
  const [database, redis, smtp] = await Promise.all([...]);
  const sefazTls = this.checkSefazTls();
  const status = !critical ? 'down' : (smtp.ok && !tlsDegraded) ? 'ok' : 'degraded';
  ```

#### Plano de Correção

Replicar o padrão do fiscal-backend nos 3 backends:

1. **auth-gateway**: adicionar checks Redis + SMTP. Critério `ok = db && redis`, `degraded = !smtp`. Inject `IORedis` (já tem).
2. **gestao-ti**: adicionar check Redis (não tem SMTP direto). Critério `ok = db && redis`.
3. **inventario** (FastAPI): adicionar check Redis via `redis.ping()`. Critério `ok = db && redis`.

```typescript
// Template (auth-gateway):
async check() {
  const [db, redis, smtp] = await Promise.all([
    this.checkDb(),
    this.checkRedis(),  // ping
    this.checkSmtp(),   // verify status
  ]);
  const critical = db.ok && redis.ok;
  const status = !critical ? 'down' : smtp.ok ? 'ok' : 'degraded';
  if (!critical) {
    // HTTP 503 explicit
    throw new ServiceUnavailableException({ status, checks: {...} });
  }
  return { status, timestamp: new Date().toISOString(), checks: {...} };
}
```

#### Esforço e validação

- **Esforço:** 30-45min por backend × 3 = **2-3h**
- **Risco:** baixo — só leitura, não muda lógica de negócio
- **Validação:**
  ```bash
  # Stop redis temporariamente
  docker compose stop redis
  curl -sk https://localhost/api/v1/auth/health -w "%{http_code}\n"
  # esperado: 503 + {"status":"down","checks":{"redis":{"ok":false,...}}}
  ```
- **Rollback:** revert do commit

### Achado #A2 — Frontend axios sem timeout configurado

- **Dimensão:** 5 (Robustez UX)
- **Severidade:** **Alto** (UX visível ao usuário)
- **Localização:** todos os 5 frontends:
  - `hub/src/services/api.ts`
  - `configurador/src/services/api.ts`
  - `gestao-ti/frontend/src/services/api.ts`
  - `fiscal/frontend/src/services/api.ts`
  - `inventario/frontend/src/services/api.ts`

- **Descrição:** Todas as instâncias `axios.create({ baseURL })` são criadas SEM a opção `timeout`. Default do axios é "sem timeout" — request fica pendente indefinidamente se backend não responder.

- **Por que é problema:**
  - Backend trava ou rede cai → usuário vê spinner infinito
  - Sem mensagem clara de erro
  - Outros requests ficam enfileirados
  - Mobile com conexão fraca: 30s+ sem feedback

- **Evidência:**
  ```typescript
  // gestao-ti/frontend/src/services/api.ts:7
  export const authApi = axios.create({ baseURL: AUTH_BASE });  // sem timeout!
  ```

#### Plano de Correção

Adicionar `timeout: 30000` (30s) em todas as instâncias `axios.create()`:

```typescript
// Padrão consistente entre frontends
export const authApi = axios.create({
  baseURL: AUTH_BASE,
  timeout: 30000,  // 30s — auditoria 10/05/2026 #A2
});
```

Para endpoints específicos que demoram mais (uploads, imports), passar override:
```typescript
fiscalApi.post('/import/produtos', formData, { timeout: 600000 }); // 10min
```

#### Esforço e validação

- **Esforço:** 15-30min total (5 arquivos, 1 linha cada)
- **Risco:** baixo — 30s é suficiente pra qualquer request normal
- **Validação:** simular backend lento (bloquear endpoint por 35s); cliente deve abortar com erro `timeout of 30000ms exceeded`

### Achado #A3 — BullMQ sem dead-letter queue / monitoramento

- **Dimensão:** 6 (Observabilidade)
- **Severidade:** **Alto** (jobs falhados invisíveis)
- **Localização:** `fiscal/backend/src/bullmq/bullmq.module.ts` + workers

- **Descrição:** Jobs que falham após 3 attempts vão para o set `failed` do BullMQ no Redis, mas:
  - Não há watcher/monitor que detecte aumento de jobs falhados
  - Não há painel (bull-board ou similar) pra debug
  - Não há alerta automático quando fila satura
  - Stuck jobs (em `active` por >N minutos) não são detectados

- **Estado atual:**
  - 3 filas: `fiscal-cruzamento`, `fiscal-scheduler`, `fiscal-alertas`
  - cruzamento.worker: ✅ retry 3 + backoff exponential
  - Outros workers: sem config explícita (default BullMQ)
  - `removeOnComplete: 1000, removeOnFail: 500` — limita histórico mas não notifica

#### Plano de Correção

**Opção A** (mínima, recomendada): adicionar monitor periódico que loga + alerta:
```typescript
// fiscal-backend/src/bullmq/queue-monitor.service.ts
@Injectable()
export class QueueMonitorService {
  @Cron('*/5 * * * *')  // a cada 5min
  async monitor() {
    for (const queue of [this.cruzamento, this.scheduler, this.alertas]) {
      const failed = await queue.getFailedCount();
      const stalled = await queue.getStalledCount();
      const active = await queue.getActiveCount();
      if (failed > 10) this.alert.notify({...});  // dispara alert
      if (stalled > 0) this.alert.notify({...});
    }
  }
}
```

**Opção B** (completa): adicionar `bull-board` em endpoint admin protegido para visibilidade UI.

**Opção C**: integrar com observability stack futura (Loki/ELK/Grafana).

#### Esforço e validação

- **Esforço:** 2-4h (Opção A) | 1 dia (Opção B + dashboard)
- **Recomendação:** **Opção A** primeiro (cobre 80% do problema com 20% do trabalho)

### Achado #M2 — Receita Federal client sem retry, fallback parcial

- **Dimensão:** 4 (Robustez)
- **Severidade:** Médio
- **Localização:** `fiscal/backend/src/cadastro/receita.client.ts`
- **Estado atual:**
  - ✅ Timeout 8s em ambos endpoints (BrasilAPI + ReceitaWS)
  - ✅ Tem fallback entre os dois (se BrasilAPI falha, tenta ReceitaWS)
  - ⚠️ Nenhum dos dois tem retry — falha pontual de rede = consulta falha
  - ⚠️ Sem cache: 2 requests rápidos da mesma chave = 2 chamadas externas
- **Plano resumido:**
  1. Adicionar 1 retry com backoff 500ms em cada client (custo baixo)
  2. Cache Redis com TTL 24h por CNPJ (Receita não muda dados em 1 dia)
  3. Esforço: 1-2h

### Achado #M3 — Endpoints POST sem `Idempotency-Key`

- **Dimensão:** 4 (Idempotência)
- **Severidade:** Médio (defesa em profundidade)
- **Localização:** todos os endpoints POST de criação (chamados, projetos, NFs, paradas)
- **Estado atual:**
  - ✅ CT-e tem dedup tripla (NSU + chave + sha256) no schema
  - ✅ `cte_documento.@@unique([cnpjConsulente, ambiente, nsu])` previne duplicata
  - ✅ Numero de chamado/OS é `@unique @default(autoincrement())` — sequencial
  - ⚠️ Sem header `Idempotency-Key` em endpoints — cliente que faça retry após timeout (network glitch) pode criar 2 chamados
  - ⚠️ Sem `unique` em `(criadoPorId, titulo, criadoEm)` ou similar — dedup só por sequência

- **Plano resumido:** adicionar middleware que aceita header `Idempotency-Key` e armazena resposta em Redis com TTL 24h. Se request repetido com mesmo key, retorna resposta cacheada. Esforço: 4-6h. Pode ser opt-in por endpoint.

### Achado #M4 — Filas BullMQ sem retry/backoff explícito (exceto cruzamento)

- **Dimensão:** 4 (Robustez filas)
- **Severidade:** Médio
- **Localização:**
  - `fiscal-cruzamento`: ✅ `attempts: 3, backoff: exponential 2s`
  - `fiscal-scheduler`: ⚠️ sem config — usa default BullMQ
  - `fiscal-alertas`: ⚠️ sem config — usa default BullMQ
- **Plano resumido:** adicionar config explícita aos jobs adicionados nessas filas. Default BullMQ é 0 retries — falha = perdido. Esforço: 30min.

## Pontos Fortes Identificados

1. **fiscal-backend health controller é o modelo correto** — DB + Redis + SMTP + SefazTLS, com 3 níveis (ok/degraded/down) e HTTP 503 quando down. Replicar nos outros.
2. **CircuitBreakerService implementado** (cruzamento) — corta chamadas SEFAZ por UF quando há erros consecutivos
3. **LimiteDiarioService** — limite 2000/CNPJ/dia hard-coded como defesa
4. **`cte_distribuicao_ativo` (freio de mão)** — admin pode parar scheduler via UI
5. **Whitelist de filiais SEFAZ** — começou restrito, escalou pra todas após validação
6. **AbortSignal.timeout em 100% das integrações backend** — Protheus, SEFAZ, alert webhook, Receita
7. **Schema CT-e com dedup robusta** — `@@unique([cnpj, ambiente, nsu])` + `chave @unique` + `xmlSha256`
8. **Adaptive backoff CT-e** — 60min se synced, 15min se há trabalho (descoberta da Fase 1)
9. **Sleep 2s entre filiais** no scheduler CT-e — espaçamento manual contra rate limit SEFAZ
10. **`PROTHEUS_API_AUTH` agora `${VAR:?}`** (após Frente 1 lote 7) — não sobe em modo degradado silencioso
11. **Audit log centralizado** (auth-gateway) — login/logout/MFA rastreáveis
12. **`removeOnComplete: 1000, removeOnFail: 500`** — limita memória Redis por fila
13. **Healthcheck do Docker em todos os containers** — pelo menos detecta processo morto
14. **`maxRetriesPerRequest: null` em IORedis** — config correta exigida pelo BullMQ
